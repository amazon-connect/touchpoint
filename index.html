New here? Set up Amazon Connect Customer and ACXD

You'll need an ACXD application with a Live Sync flow, and an Amazon Connect Customer instance that routes contacts into it.

  1. Build the ACXD application. In the ACXD Canvas, wire Start → a Live Sync node → Exit application. On the Live Sync node, declare the actions and scopes the assistant may use (or define them on the fly with this SDK for rapid prototyping).
  2. Publish it and copy your keys. Deploy the application, then from its settings copy the deployment key and API key into the fields above.
  3. Point Amazon Connect at it. In your Amazon Connect Customer instance, create a contact flow that hands the contact to your ACXD application; note the instance ID and contact flow ID.
  4. Stand up the browser endpoints so the page can create a contact: StartChatContact (chat) and StartWebRTCContact (voice).

Welcome to Touchpoint

Touchpoint is a drop-in conversational UI and SDK for web and mobile apps. It natively supports text chat and voice — plus Live Sync, multimodal technology that synchronizes any two channels — for example a voice or chat conversation with the page. Get started below, then explore the Live Sync capabilities.

Getting started

Create a Touchpoint instance with your Amazon Connect Customer details and pick an input mode — text, voice, voiceMini, or external (no UI, for Live Sync only). The snippet below reflects the details you entered on the launch form.

Tip Touchpoint also supports Live Sync — the liveSync block in create() connects it, so the assistant can drive the page. See the Live Sync section below. 

import { create } from "@amazon-connect-touchpoint/web";

const touchpoint = await create({
  config: {
    chatEndpoint: "…",   // StartChatContact (chat)
    voiceEndpoint: "…",  // StartWebRTCContact (voice / voiceMini)
    instanceId: "…",
    contactFlowId: "…",
    region: "us-west-2",
  },
  input: "voiceMini",
  liveSync: {
    deploymentKey: "…",
    apiKey: "…",
    // contactId is optional — defaults to the active session's contact ID.
  },
});

// Explicitly advertise scope + actions (sent once the session has a contact ID):
await touchpoint.sendContext({
  scopes: ["booking"],
  actions: [ /* custom actions, shown per example below */ ],
});

Live Sync

Live Sync lets the assistant drive this page while you talk to it. Most page controls are driven by custom actions: you register a named action with a JSON Schema, the assistant resolves what the user said into typed arguments, and your handler applies them to the page. Use the floating mic (bottom-right) and speak the prompts in each capability below.

Actions are typically configured in ACXD — in the Canvas, as settings on the Live Sync node — so they're part of your deployed conversation design. This SDK also lets you define actions on the fly (as shown in the snippets below), which is ideal for rapid prototyping.

External mode drives this page from a separate live contact. Set liveSync.contactId to that contact — most commonly an inbound phone call — so the caller's conversation drives the page Touchpoint is installed on. Bind one below.

Getting a phone call's contact ID onto the page

With an inbound phone call, the page needs the call's contact ID to bind Live Sync to it. A few practical patterns:

  • SMS deep link. During the call, send an SMS with a deep link to your digital asset (website / mobile app) and the contact ID appended as a query parameter (e.g. ?contactId=…). The page reads it on load and passes it to liveSync.contactId.
  • OTP handshake (no SMS). The caller is on the phone and the digital asset at the same time:
    • The asset shows a “connect” prompt asking for a code.
    • On the call, the assistant asks “Are you ready for the code?” — the user says “yes”.
    • The assistant reads out a one-time code.
    • The user enters it on the asset.
    • Your backend exchanges the OTP for the contact ID — eliminating the need for SMS.
  • Authenticated correlation. The user is already signed in on the digital asset. When they call, the IVR identifies them (caller ID / account lookup) and your backend maps that identity to the open session, injecting the contact ID server-side — no manual step for the user.
  • Scan-to-connect (QR / short code). The asset shows a QR code or short code; the caller scans or reads it back on the call, and your backend links the scanned token to the active contact ID.

Text field

Capture free-text values (name, email) as typed arguments and set them on the inputs.

When to use names, emails, notes — any free-form value.

My name is Jane Doe and my email is jane@example.com. 
{
  action: "set_contact_info",
  description: "Set the customer's name and email",
  schema: {
    type: "object",
    properties: {
      fullName: { type: "string" },
      email: { type: "string" },
    },
  },
  handler: ({ fullName, email }) => {
    setValue("fullName", fullName);
    setValue("email", email);
  },
}

Dropdown

Constrain the argument to the allowed options with an enum, then set the <select>.

When to use a fixed set of mutually-exclusive options kept compact.

Set the cabin class to business. 
{
  action: "set_cabin_class",
  description: "Choose the cabin class",
  schema: {
    type: "object",
    properties: {
      cabin: { type: "string", enum: ["economy", "premium", "business", "first"] },
    },
    required: ["cabin"],
  },
  handler: ({ cabin }) => setValue("cabin", cabin),
}

Single choice (radio) — choosing a flight

Give the model the list (ids + the details it should reason over) and let it resolve natural phrasing to one id. Describe the options in the schema so “the second one”, “before noon”, and “the cheapest” all map correctly.

When to use pick-one lists where the user describes the option rather than reading an id.

I'll take the second one.
The one that leaves before noon.
Give me the cheapest flight.
{
  action: "select_flight",
  description:
    "Select a flight. Options: BLU101 (8:15am, $312), BLU208 (11:40am, " +
    "$289), BLU330 (2:05pm, $255), BLU412 (6:30pm, $270).",
  schema: {
    type: "object",
    properties: {
      flightId: { type: "string", enum: ["BLU101", "BLU208", "BLU330", "BLU412"] },
    },
    required: ["flightId"],
  },
  handler: ({ flightId }) => setChecked("flight", flightId),
}

Multi-select (checkbox)

Accept an array argument and check every matching box — the caller can pick several at once.

When to use add-ons and preferences where more than one choice can apply.

Add a checked bag and travel insurance. 
{
  action: "set_extras",
  description: "Select trip extras (any number)",
  schema: {
    type: "object",
    properties: {
      extras: {
        type: "array",
        items: { type: "string", enum: ["bag", "legroom", "insurance", "priority"] },
      },
    },
    required: ["extras"],
  },
  handler: ({ extras }) => setChecked("extras", extras),
}

Date & time

Take normalized date / time strings and set the native inputs — the assistant turns “next Friday at 6pm” into YYYY-MM-DD / HH:mm.

When to use scheduling — appointments, departures, reservations.

Depart next Friday at 6:30 in the evening. 
{
  action: "set_departure",
  description: "Set the departure date and time",
  schema: {
    type: "object",
    properties: {
      date: { type: "string", description: "YYYY-MM-DD" },
      time: { type: "string", description: "24h HH:mm" },
    },
  },
  handler: ({ date, time }) => {
    if (date) setValue("departDate", date);
    if (time) setValue("departTime", time);
  },
}

Button

A button isn't a value — expose an action whose handler triggers the click.

When to use submit / search / continue and other on-page buttons you want the assistant to press.

Search for flights.
{
  action: "search_flights",
  description: "Run the flight search",
  handler: () => document.getElementById("searchBtn").click(),
}

Free-form action

Actions aren't limited to form controls — any app behavior can be a custom action.

When to use domain actions like “add to cart”, “apply a coupon”, “switch to dark mode”.

Add two coffees to my order.
order:
0 item(s) 
{
  action: "add_to_order",
  description: "Add one or more items to the customer's order",
  schema: {
    type: "object",
    properties: {
      item: { type: "string" },
      quantity: { type: "number" },
    },
    required: ["item", "quantity"],
  },
  handler: ({ item, quantity }) => addToOrder(item, quantity),
}

Navigate the page

Navigation is modeled as a custom action — navigate — whose section argument is an enum of the reachable sections. The assistant resolves what the customer said (“go to the button example”) into a section name, and the handler scrolls there. An explicit action with an enumerated target routes far more reliably than free-form phrasing.

When to use multi-step flows and multi-page sites — “go to the button example”, “show me the dropdown”, “take me to script steps”.

Go to the button example.
Show me the dropdown.
Take me to script steps.
// Register navigation as a custom action:
await touchpoint.sendContext({
  actions: [
    {
      action: "navigate",
      description:
        "Scroll to / open a section of this page. Use whenever the user " +
        "asks to go to, show, open, or jump to a section.",
      schema: {
        type: "object",
        properties: {
          section: {
            type: "string",
            enum: ["Getting started", "Text field", "Button", "Script steps", /* … */],
          },
        },
        required: ["section"],
      },
      handler: ({ section }) => scrollToExample(section),
    },
  ],
});

Live Sync script steps
